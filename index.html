A packing simulator that generates new trajectories on demand.

A person packs a suitcase in a two-room apartment. Each episode is an executable task, a persona and a private schedule of mistakes. A scripted user replans after every action, and every action is grounded in a contact-only MuJoCo simulation with anatomical hands. The same case can unfold differently, and each run is rendered and logged as training data.

How the simulation works

The design follows the environment construction of interactive-assistant benchmarks: an executable task rather than a recorded demonstration, semantic actions with a grounder, goal predicates instead of a reference route, and progress-conditioned events. Here it is specialised to packing.

1 · CaseTask (what to pack), seed, persona and a private event schedule. Each case is dry-run symbolically first; schedules whose events cannot fire are rejected.
2 · UserA replanning policy over the symbolic state. Events take over its action queue: a wrong pile, a skipped item, the lid shut early.
3 · PackSimSymbolic state, preconditions, effects and goal predicates. A refused action returns feedback and changes nothing.
4 · ExecutorGrounds each accepted action in MuJoCo with contact-only skills, verifies the physical outcome, then commits it. Any action can be rewound.
5 · Record25 Hz poses, the action log with labels and frame ranges, physical checks and goals. Blender Cycles renders the head and room cameras.

State

Where the person stands and what they face; what they hold; each item's location (home station, hands, or a region of the case) and stacking order; the bottle's orientation; whether the lid is open or closed and the case zipped; whether the case is on the bed or upright on the floor; and the current packing list, which a plan change can edit. Physical state (body poses, contacts, lid angle) lives in MuJoCo and is cross-checked against the symbolic state at the end of every run.

Goal predicates

Success is a set of predicates, not a route, so any valid order passes: packed(x) for every listed item, no_extra_items, bottle_upright, heavy_on_floor(x) (the trousers and toiletry bag rest on the case floor), nothing_on(camera), lid_closed, zipped and case_upright.

Action space

Semantic actions separate the reference from the execution. Arguments in angle brackets are resolved by the grounder: a text form such as pick up the T-shirt pile parses to pick_up(tshirts). If grounding fails or a precondition does not hold, the user gets feedback (for example "your hands are full" or "the towel is under the T-shirt pile") and the world does not change.

Progress-conditioned events

An event has a semantic trigger (for example "about to fetch the sweatshirts" or "after three items are packed"), targets, the actions it injects, and a completion condition. While active it owns the user's action queue, then hands control back. With self-recovery on, the user corrects the mistake (puts the wrong pile back, remembers the forgotten item before closing, reopens the lid). With it off, the error stays in the world and shows up as a failed goal. Questions and plan changes use separate, non-error channels. Schedules are checked for distinct targets, events that actually fire, and separated windows.

Every case is new: the order within each packing phase, the regions chosen, the persona's pace and the events all come from the seed. The task library:

Each trajectory folder holds case.json (task, persona, private schedule), actions.json (one record per action: text, label of nominal, error, recovery, question or plan change, event id, start and end time and frame, feedback, symbolic state after), goals.json, frames.json (every body pose at 25 Hz), events.json (lift, placement, lid and zip checks), validation.json and the videos.

What is simulated, and the limitations
  • MuJoCo at 1 kHz with gravity. Two anatomical MyoHand hands (23 joints each) with torque-limited finger servos on force-limited wrist carriages. No welds or equality constraints: items rise, travel and settle through contact only.
  • Targets come from the live state: stand points from where an item is now, drop heights from the piles already in a region.
  • The body is kinematic, solved around the simulated forearms with fixed segment lengths: no balance, foot forces or whole-body collision. Pelvis clearance is checked geometrically.
  • Garments are compliant rigid piles, not cloth: a pile is picked and placed as one folded unit. The scans have no separate garments to unstack.
  • The zipper is idealised: after a closure check, the lid hinge range is narrowed to the closed pose. The hinge sits at mid-depth so both halves lie flat, standing in for the fabric hinge. A thin zip-track lip on the lid is what the fingertips catch when opening it.
  • Standing the case up uses a two-hand overhand grip on the trolley bar, tested with a short pull. A grip that slips is released and retried with the hands placed differently (a re-grip). Closing the lid works the same way. Every attempt is logged in events.json.
  • If an action still fails physically (for example, the bottle tips over as it is set down), the generator rewinds physics, recordings and symbolic state to just before that action and retries it with a small variation in stand position and timing, up to three times. The saved trajectory is a single continuous run; the retries are logged as action_retry events. A case that still fails is rejected.
  • The user is scripted, not a learned human model. Events cover a controlled taxonomy and do not exhaust real mistakes.
  • Masses, friction and finger strengths are assumed values. Nothing is calibrated sim-to-real.
